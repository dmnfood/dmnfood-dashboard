# 학교급식 발주: 원문 근거를 함께 확인하는 흐름

이 문서는 2026-10-21부터 설명받은 업무 규칙과 구현 이력을 기록한다. 현재 기준은 아래 최신 개편이며, 이후 날짜별 기록에는 이전 화면의 설계도 포함된다. 메일 본문은 네이버웍스로 이동해 확인하며 화면에서 대조하는 대상은 첨부 원본이다.

## 최신 마무리: 수정 · 확정 목록 · 확정 상태

2026-10-22 추가 요청을 반영한다. 아무 자료도 선택하지 않은 초기 안내는 오른쪽 섹션 가운데에 정렬하고, 상단의 별도 세 단계 설명은 제거한다. 선택 이후의 업체 확인·원본 대조·최종 확인 카드는 유지한다.

- 원본 대조 카드의 `수정하기`에서 수정 내용을 입력하고 분석에 반영한다. 기존 원본 근거 검증과 재분석 경로를 사용하며, 수정 후에는 업체 확인과 원본 대조를 다시 받는다. 확정한 분석은 수정할 수 없다.
- 최종 확정한 결과는 상단 `등록된 발주 → 확정한 발주`에서 업체·상품별 수량·확정 시각·출처로 조회한다. 최근 확정순 25건씩 불러오고 거래처 검색·더 보기·원본 대조 화면 연결을 제공한다. 기존 수동 등록 건은 같은 창의 `수동 보완`에서 유지한다.
- 확정 목록은 기존 `orderAiAnalyses`의 확정 결과를 조회한다. 별도 발주 레코드를 중복 생성하지 않으며, 기존 관리자·매니저 권한으로 읽는다. 원문 보관 기간이 지난 후에도 확정 요약은 조회할 수 있다. 원문·사진의 30일 보관 정책은 유지한다.
- 메일 목록은 확정 성공 즉시 `발주 확정`으로 표시한다. 저장된 확정 결과와 정기 상태 조회에서도 복원하며, 늦게 도착한 분석 준비·실패 응답이 확정 표시를 되돌리지 않는다. 최근 7일 밖의 메일도 화면에 불러온 목록에 한해 저장 분석과 원본 해시를 읽어 대조하므로, 확정 목록 첫 25건 밖의 오래된 발주도 표시한다. 이 조회로 AI를 호출하거나 오래된 미분석 메일을 자동 분석하지 않는다. 확정 완료 카드의 `등록된 발주 보기`도 같은 목록을 연다.
- 확정은 담당자가 확인한 내용의 저장이며 ERP 판매 입력·출고는 별도 후속 연결 단계다.

## 열린 발주함에서 사전 분석 · 한 화면에서 대조와 확정

2026-10-22 사용자는 **대시보드가 열려 있을 때 자동 처리**를 선택했다. 승인된 관리자·매니저가 발주 페이지를 열면 학교급식 메일함(106)의 최근 7일 자료를 확인하고, 약 2분마다 다시 수집한다. 메일을 선택하지 않아도 분석되지 않은 자료를 하나씩 분석해 초안으로 저장한다. 페이지를 닫은 동안의 예약 수집은 이번 범위에 포함하지 않는다.

- 메일 연결 상태는 상단의 `학교급식 업체 관리` 왼쪽에 작게 표시한다. 연결 설정과 수동 수집은 상태 버튼에서 연다.
- 자동 수집과 메일함 목록 확인이 겹쳐 작업 잠금이 걸리면 정상 연결 표시는 유지하고 폴더 조회만 제한적으로 재확인한다. 조회가 보류되는 동안 수동 수집은 막는다. 실제 계정·폴더 변경 오류는 계속 확인이 필요하며, 이 처리가 AI 재시도를 유발하지 않는다.
- 왼쪽 발주함은 `분석 대기 / 분석 중 / 확인 준비 / 다시 확인 필요`를 표시한다. 기존 분석이 있으면 다시 AI를 호출하지 않고 저장된 결과를 연다. 자동 분석 범위 밖의 과거·다른 메일함 자료와 카톡·문자·사진은 수동 분석 버튼을 유지한다.
- 오른쪽은 `1 거래처 확인 / 2 원본 대조 / 3 최종 확인`의 세 카드로 분리한다. 추정 학교급식 업체를 `맞아요`로 확인하거나 옆의 `수정`에서 변경한다. 단순 업체 확인으로 AI를 재호출하지 않는다.
- 원본 카드에서 Excel·사진·텍스트의 포함 상품 행을 함께 강조하고, 오른쪽에는 전체 상품명과 합계만 쌓아 표시한다. 인식행·제외행 선택 버튼과 파일명·행/셀 설명은 제거한다. 담당자는 강조한 행과 나머지 원본 맥락을 함께 보고 단일 `원본 대조 완료`를 누른다. 제외한 행을 따로 선택·완료할 필요가 없다. 포함 상품의 모든 원본 파일·시트·근거 페이지는 열람해야 완료할 수 있으며 원본 해시와 수량 검사는 유지한다. 왼쪽의 첨부파일 열기는 별도 원본 열람으로 유지한다.
- Excel의 시트명 위치에 작은 시트 탭을 둔다. 시트 선택 드롭다운과 시트·행열 범위 안내를 없애고, 열 너비를 현재 카드 폭에 맞추며 긴 글은 줄바꿈한다. 원본 데이터·주소·수식 계산값·합산 결과는 변경하지 않는다. 최소 가독 너비보다 좁은 화면에서는 스크롤을 유지한다.
- 업체 목록은 목록 전체 버전을 모든 업체에 부여하므로 다른 업체의 추가만으로도 과거 분석의 버전이 달라질 수 있다. 같은 학교업체 ID·이름이 유지된 경우에는 `/api/order-ai/analysis`의 `action:refresh-customer`로 원본·수량·그룹이 완전히 같은지 재검증한 뒤 목록 버전만 갱신한다. AI를 호출하지 않으며 분석 이력을 보존하고 사람의 확인은 다시 받는다. 별도 법인·이름 변경·삭제는 자동 연결하지 않고 업체 선택을 요구한다. 실패한 갱신은 자동 반복하지 않는다.
- 하단의 `발주 확정`은 별도 카드에 있다. 업체·단일 원본 대조·원본 해시·분석 버전·최신 업체 목록·온라인 상태 검사를 통과해야 한다. 원본 대조 완료에는 강조한 상품과 나머지 행의 맥락 확인을 포함하여 기존 서버의 상품별·제외 맥락 확인값으로 저장한다. 수정하면 해당 확인을 해제한다. 작업 중 도착한 새 분석이 담당자의 수정·대조 내용을 덮어쓰지 않는다.
- 여러 직원이나 탭이 열려 있어도 `orderAiJobs/{원본 ID}`의 원자적 작업 선점과 기존 분석 잠금으로 중복 호출을 막는다. 실패하거나 응답 여부가 불확실한 분석은 자동 재시도하지 않고 담당자의 직접 재시작을 기다린다. 기존 초안·확정 결과는 보존한다.
- `/api/order-ai/background`는 기존 status 함수의 내부 분기로 처리한다. 학교급식 폴더 소속·최근 7일·계정·원본 해시를 교차 검증하며, 직원에게 메일 인증정보 조회 권한을 부여하지 않는다. 작업 기록에는 원문이나 첨부를 중복 저장하지 않는다.
- 자동 처리는 수집과 분석 초안 저장까지다. 사람의 최종 확정, ERP 판매 입력, 출고, 송장 발송을 자동 실행하지 않는다. 운영 Ecount 판매 입력 API 연결은 남아 있다. 원문·사진의 기존 30일 보관 및 무료 정리 방식은 유지한다.

## 진행 현황 보고 방식

사용자가 **“진행 현황 알려줘”**라고 요청하면 기존 발주 자동화 로드맵과 같은 시각화 양식으로 보고한다. 자료 수집부터 원본 확인, 거래처 선택, 범위 지정, 상품 연결, 수량 계산, 원본 대조, 최종 확정, ERP 입력, 출력·회신까지 논리 순서로 표시한다. 각 단계에 실제 운영 확인 완료 / 구현 완료·연결 확인 필요 / 다음 작업을 구분하고 근거 없이 완료율을 만들지 않는다. 현재 병목과 바로 다음 작업도 함께 표시한다.

## 현재 운영 화면의 입력 방식

- 거래처는 자동 확정하지 않는다. Ecount의 실제 코드·거래처명을 직접 등록하거나 CSV·Excel 첫 시트에서 가져온 목록에서 검색·선택한다. 코드의 선행 0은 유지한다.
- 발주행은 거래처별 자동 규칙 대신 담당자가 첨부 원본의 셀을 드래그해 범위를 지정한다. 주소 입력과 모바일 두 모서리 선택도 지원한다. 첫 구현은 첨부파일당 하나의 연속 직사각형 범위다.
- 화면은 `거래처·원본 → 범위 지정 → 상품·수량 연결 → 대조·확정` 순서다. 마지막 두 단계는 아직 실행하지 않는다. 별도 등록된 기존 발주는 별도 창에서 열어 선택한 메일의 해석 결과로 오인하지 않도록 한다.
- 저장 대상은 `mailPreparations/{메일 원본 ID}/attachments/{첨부 ID}`다. 원본 메일 해시·첨부 해시·거래처 코드/이름/버전·시트/셀 범위·담당자·시각·수정 전 이력을 함께 보존한다. 범위 저장은 발주 승인이나 ERP 판매 입력이 아니다.
- 원본·거래처 최신 정보·저장 버전이 다르면 덮어쓰지 않고 다시 확인한다. 오프라인·서버 확인 전에는 저장 완료로 표시하지 않는다.
- 2026-10-21 사용자가 기존 Ecount 연결은 이전 실험용 API여서 현재 동작하지 않는 것이 맞다고 확인했다. 운영 장애로 분류하지 않고 **운영 API 전환 예정**으로 관리한다. 거래처 직접 등록·가져오기와 범위 지정은 별도로 진행할 수 있다.

## 대화형 AI 발주 분석

2026-10-21 사용자는 수동 4단계 화면 대신 AI가 자료를 먼저 분석하고 담당자는 질문 응답·원본 대조·최종 확정을 하는 대화형 흐름을 요청했다. 사용자가 Vercel Production에 `OPENAI_API_KEY` 저장을 완료했다고 확인했다. 키 존재와 실제 제공자 호출 성공은 별도로 검증한다.

- 왼쪽 메일 목록을 유지한다. 오른쪽에 선택한 메일 정보와 `발주 분석 시작` 버튼을 두고, 실행 뒤 대화형 분석·확인 화면으로 이어진다.
- AI가 등록된 거래처 목록에서 후보를 찾고, 원본의 시트·발주 범위·상품·규격·수량 칸을 식별해 초안을 만든다. 목록에 없는 거래처·상품 코드를 만들어내지 않고, 애매한 항목만 담당자에게 질문한다.
- 웹앱 전용 GPT에 회사 제품 목록·확정한 업무 규칙·거래처 목록과 현재 원본을 전달한다. 이 채팅의 기억이 웹앱 API에 자동 공유된다고 가정하지 않는다. 상품 상세 해석 규칙은 사용자가 기존 발주서를 다시 검토하기로 했으므로 미확정 규칙을 확정된 사실로 주입하지 않는다.
- 각 분석 항목에 원본 파일 해시와 Excel 시트·셀 주소 또는 이미지 근거 영역을 연결한다. 실제 합산은 원본 행의 수량으로 프로그램이 재계산한다. 읽지 못하거나 제외한 행·시트·첨부도 누락 없이 확인 대상으로 관리한다.
- 기본 대화에서는 원본을 상시 크게 표시하지 않고, 원본 대조 시점에 분석 결과와 함께 보여준다. 같은 상품의 근거 행을 동시에 강조하고 수량·단위·합계를 대조한다. 담당자는 필요하면 언제든 원본을 열 수 있다.
- 대화 중 긍정 표현을 최종 승인으로 간주하지 않는다. 담당자가 대조한 동일 분석 버전에 명시적인 `최종 확정`을 실행하고, 수정되면 관련 확인을 해제한다. ERP 판매 입력은 별도 후속 연결 단계다.
- AI 연동 인증값은 서버 전용 보관소에 저장하며 채팅·브라우저·소스 코드에 노출하지 않는다. 처음에는 가상 자료로 분석·대조를 검증한 뒤 실제 메일 한 건으로 점검한다.

### 이번 구현 범위와 연결 점검

2026-10-21 후속 개편: GPT 분석은 유지하고 화면은 `분석 확인 → 원본 대조 → 최종 확인`의 세 단계로 정리한다. 현재 단계만 표시하고 과거 질문·답변은 접힌 분석 기록에 보관한다. 단계 이동 자체는 확정이 아니며, 마지막 화면의 명시적 `발주 확정`을 누를 때만 확정 요청을 보낸다.

거래처 선택은 학교급식 주간현황표의 등록 업체를 기준으로 한다. 기존 브라우저의 업체 목록을 공용 `settings/schoolMealCompanies`로 최초 한 번 옮기고, 공용 목록이 이미 있으면 덮어쓰지 않는다. 주간현황표에서 관리한 업체를 발주 화면과 서버가 같은 버전으로 사용한다. 업체 이름과 내부 ID를 보존하며 ERP 거래처 코드를 만들어내지 않는다. ERP 코드 없이도 원본 대조·발주 확정은 가능하고, 실제 판매 전송 전에는 ERP 코드 연결이 별도로 필요하다.

- 거래처 상품명과 회사 상품명은 다르다. 실제 상품명 대응표는 사용자가 별도로 제공한다. 임의의 실제 매핑을 만들지 않는다.
- 수량은 **항상 각 행의 수량 칸을 합산**한다. 제품이 등장한 행 수를 수량으로 사용하지 않는다.
- 발주 담당자(사무 담당자와 대표)가 자동 인식 내용을 원문과 함께 대조한다. 담당자의 수동 등록 후 다른 사람에게 결재받는 흐름이 아니다.

## 화면의 진행 순서

1. 자료 도착과 보관 상태를 알린다. 해석 중·확인 준비·추가 확인 필요를 구분한다. 제목·첨부를 받았다는 사실을 발주 내용을 정확히 인식했다는 뜻으로 표시하지 않는다.
2. ERP 거래처를 목록에서 선택하고 원본 Excel의 발주 범위를 직접 지정한다. 대상 주간·자료 종류·신규/추가/수정 관계와 원본 파일·페이지·시트 준비 상태를 확인한다.
3. 원문 왼쪽과 해석 결과 오른쪽을 함께 표시한다. 같은 회사 제품으로 인식한 모든 행을 동시에 강조한다. 상품명뿐 아니라 수량·단위·규격의 근거도 표시한다.
4. 제품별로 각 행의 수량과 합산식을 보여준다. 예: `2행 2병 + 3행 1병 + 5행 3병 = 6병`. 담당자가 수정하거나 원문 대조 완료를 누르면 다음 제품으로 이동한다.
5. 모든 원문과 제품의 대조가 끝나면 원문 화면에서 최종 결과 화면으로 이동한다. 제품별 합계와 원래 납품 일정·납품처 내역을 함께 확인한다.
6. 최종 확인된 버전을 고정하고 서버가 ERP 전송 작업을 만든다. 등록 중·등록 확인·일부 실패·등록 여부 확인 필요를 구분하고 실제 전표 식별자를 결과에 연결한다.

제품별 묶음은 확인 편의를 위한 단위다. 거래처 발주서의 납품일·학교·납품처 정보는 원래 행에 남긴다. 거래처의 학교 납품일과 우리 회사의 출고일·ERP 전표일은 별도 개념이다. 최종 ERP 집계 단위와 전표일은 실제 회사 업무에 맞춰 설정한다.

## 자료별 원문 근거

| 자료 | 원문 보관 | 강조할 위치 |
| --- | --- | --- |
| Excel | 첨부 파일 자체와 해시, 형식을 유지한 열람 자료 | 파일·시트·행·상품/수량/단위/날짜 셀 범위 |
| 이미지·PDF | 원본 파일과 해시, 원본 크기 | 페이지와 원본 좌표에 연결된 영역 |
| 제목·본문·문자 | 필드별 원문 문자열과 해시 | 해당 필드의 문자 구간 |

Excel을 임의로 재구성한 표는 원본 그대로라고 표시하지 않는다. 실제 원문 열람에서는 병합 셀, 숨김 행·시트, 여러 페이지, 잘린 이미지까지 확인 범위를 관리한다. 수량 셀의 수식·표시값이 다르거나 읽을 수 없으면 미확정으로 남긴다.

메일 본문, ERP 링크, Excel 첨부에 같은 주문이 반복되어도 각각 별도 발주 수량으로 합산하지 않는다. 거래처 양식별로 계산 기준 자료를 정하고, 같은 내용의 표현은 근거로 연결한다. ERP 접근 버튼은 발주서 데이터이며 임의 외부 접속·입력 명령으로 취급하지 않는다.

## 상품·수량 해석과 누락 방지

- 거래처별 상품명 대응표에는 원문 이름·원산지·규격·포장·단위와 회사의 정확한 품목 코드를 연결한다. 원문 이름이 비슷하다는 이유만으로 다른 상품을 합치지 않는다.
- 단위가 다르면 승인된 환산 규칙을 먼저 적용한다. 박스당 병 수가 정해지지 않았으면 합산·확정을 막는다. 원문 수량과 환산 결과, 사용한 규칙을 함께 남긴다.
- AI는 상품·수량·근거 위치의 후보를 제안한다. 합계는 확정된 행의 값을 프로그램으로 계산한다. AI가 만든 합계 숫자만 승인 근거로 사용하지 않는다.
- 대상 범위의 행/영역은 `제품 수량에 포함 / 사유를 남기고 제외 / 미해결` 중 하나에 속해야 한다. 미해결을 숨기거나 0으로 바꿔 최종 확인을 통과시키지 않는다.
- 제목·헤더·소계·합계 행은 상세 행과 중복 합산하지 않는다. 다른 업체 상품은 거래처 규칙과 원문 근거로 제외하며, 우리 상품인지 불명확한 행은 확인 대상으로 남긴다.
- 파일·페이지·시트 누락, 읽을 수 없는 수량, 미확정 상품, 불명확한 단위가 있으면 최종 확인을 막는다.

## 추가·수정 발주

거래처, 발주번호, 대상 주간, 학교·납품처 등을 이용해 기존 발주와의 관계 후보를 찾는다. 자료 도착 시각만으로 이전 발주를 덮어쓰거나 주간 합계에 더하지 않는다.

| 구분 | 확인할 의미 |
| --- | --- |
| 신규 | 별개의 새 주문 |
| 추가 | 기존 수량에 더할 수량 |
| 전체 교체 | 새 자료가 기존 전체 내용을 대체 |
| 일부 수정 | 지정한 행·제품·일정만 변경 |
| 취소 | 지정한 범위의 취소 |
| 관계 미확정 | 담당자가 의미를 확인하기 전 처리 보류 |

예를 들어 기존 6병에 새 자료가 2병이라고 적혀 있어도, 추가라면 8병이고 전체 수정이라면 2병이다. 변경 화면에는 이전·변경 후 수량·증감과 두 원문을 함께 표시한다. 원문과 이전 확인 버전은 보존한다. ERP 입력 뒤 도착한 수정 자료는 새 판매 전표를 무조건 추가하는 대신 회사의 정정 절차로 연결한다.

## 확인 기록과 ERP 전송

제품 확인은 `원문 해시 + 해석 버전 + 상품 대응표 버전 + 대상 행 + 계산 결과`에 결합한다. 상품·수량·근거가 바뀌면 해당 제품의 확인과 전체 최종 확정을 해제한다. 다른 담당자의 변경은 현재 발주함의 버전 충돌 방지 방식을 확장해 처리한다.

ERP 전송은 다음 조건을 만족해야 한다.

- 담당자가 최종 확인한 동일 버전만 서버가 전송한다. 브라우저에서 넘어온 임의 품목·수량을 그대로 ERP에 쓰지 않는다.
- 거래처 코드, 회사 품목 코드, 단위, 전표일, 창고·단가·세금 등 회사 필수 항목을 검증한다. 상품 대응표를 받기 전에는 실제 코드로 자동 매핑하지 않는다.
- 발주·확정 버전·ERP별로 하나의 전송 작업을 만들고 중복 클릭·동시 실행을 막는다.
- 요청 시간 초과는 등록 실패로 단정하지 않는다. 이미 등록됐을 수 있으므로 자동 재전송하지 않고 등록 여부를 대조한다.
- HTTP 성공만으로 등록 완료라 하지 않는다. 항목별 처리 결과와 실제 전표 식별자를 확보한다. 일부 성공이면 성공·실패 항목을 분리한다.
- 최종 확인 뒤 ERP 전송 전 수정 자료가 도착한 경우, 기존 전송 작업과의 관계를 확인할 수 있도록 보류 상태를 둔다.

이카운트 공식 안내에는 판매 입력 API와 사전 테스트가 명시되어 있다. 정확한 요청·응답 규격과 회사 필수값·재조회 수단은 로그인 후 회사 API 매뉴얼로 확인해야 한다. 판매 입력은 재고 차감·미수금 반영을 수반하므로 기존 회사의 판매 전표 종류·기준일·집계 방식을 재현해야 한다.

## 다음 구현의 데이터 경계

1. `수신 자료`: 채널 식별자, 수신 시각, 발신자, 원본·해시와 보관 위치.
2. `문서/행/영역`: 시트·페이지·문자·좌표, 원문 값, 포함/제외/미해결 상태.
3. `해석 버전`: 거래처 양식·상품 대응표 버전, 후보 품목 코드, 수량·단위와 계산 근거, 원래 납품 일정.
4. `검토 버전`: 제품별 확인, 원문 범위 확인, 최종 확정 내용·담당자·시각.
5. `ERP 작업`: 확정 버전과 고정된 전송 내용, 상태·시도·응답·전표 식별자·대사 결과.

현재의 발주 스키마 1은 텍스트 원문, 최대 5품목, 발주 전체에 하나의 납품일을 갖는다. 새 흐름은 UI뿐 아니라 저장 구조·보안 규칙·알림 대상을 함께 확장해야 한다. 수집 계정은 발주를 확정할 권한을 얻지 않으며, 실제 운영 연결 전까지 기존 확인 화면과 서버 권한은 변경하지 않는다.

## 구현 순서

1. 가상 주간 발주서로 동일 제품의 다중 행 강조·수량 합산·수정 후 재확인·최종 합계 흐름을 점검한다.
2. 실제 메일의 Excel 첨부 보관·열람을 연결하고 양식 한 종류를 우선 지원한다.
3. 사용자가 제공한 거래처별 상품 대응표와 실제 발주 양식으로 행별 근거·수량·예외를 검증한다.
4. 검증된 해석 결과를 확인 요청 알림과 연결한다. 정기 수집은 독립된 서버 작업으로 운영한다.
5. 실제 회사 판매 전표와 공식 API 매뉴얼을 기준으로 이카운트 시험 환경에서 전송·대사·중복 차단을 검증한다.
6. 최종 확인된 건의 운영 ERP 전송을 연결한다. 카카오톡 캡처·문자는 같은 근거 확인 구조에 별도 수집 연결을 붙인다.
