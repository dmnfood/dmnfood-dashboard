# 발주 알림과 검토 승인

업무의 목표는 **발주를 자동으로 수집·추출하고, 발주 담당자가 원문과 추출 결과를 대조하여 확정하는 것**입니다. 담당자가 발주를 직접 입력한 뒤 다른 사무 담당자에게 결재받는 절차가 아닙니다. 이 문서의 "확인·승인"은 자동 수집·인식의 오류를 사람이 확인하여 바로잡고 다음 처리에 사용할 내용을 확정한다는 의미입니다.

현재 기능은 `orderRequests` 발주함의 알림·원문 대조·수정·확정 단계와 네이버웍스 메일 연결·최근 7일 원문 시험 수집·첨부 열람입니다. 실제 메일 계정은 서버 설정과 OAuth 동의 후 연결하며, 현재 원문 시험 수집은 **학교급식 발주** 메일함으로 고정하고 담당자가 버튼으로 시작합니다. API 응답 본문과 첨부 정보는 서버에 보존하되 화면에서는 첨부 원본을 중심으로 보여 주며, 메일 본문은 네이버웍스에서 엽니다. 지원하는 일반 Excel/CSV 첨부는 열람할 때 원본 파일을 별도로 보관합니다. 거래처별 발주 해석·상품 연결과 정기 자동 수집은 아직 활성화하지 않았습니다. 카카오톡·아이폰 문자·현대 ERP는 연결 전입니다. 직접 접수는 자동 수집 장애나 누락을 보완하는 수단이고, 명시적으로 표시된 가상 발주는 흐름을 시험하는 용도입니다. 현재 화면의 승인은 ERP 등록·송장 발급·메신저 발송·출고를 실행하지 않습니다.

## 사용 흐름

1. 승인된 매니저 또는 관리자 계정으로 로그인합니다.
   메인 대시보드의 **일반 사무 → 발주 확인·승인** 카드 또는 **전체** 탭의 같은 카드에서 발주함을 엽니다.
2. 상단의 작은 메일 상태 영역에서 관리자가 **메일 가져오기**를 누르면 학교급식 발주 메일함의 최근 7일 자료를 가져옵니다. 계정·서버 연결 정보는 관리자 전용 **연결 설정** 팝업에서 확인합니다. **발주함** 왼쪽 메일 목록은 학교급식을 기본으로 보여 주며, 필요하면 **전체 수집 메일**로 이전 수집 기록도 확인합니다. 오른쪽 **첨부 원본 확인** 탭에서 Excel/CSV를 열거나 내려받고, 본문은 **네이버웍스에서 메일 열기**로 확인합니다. 원문·첨부는 읽기 전용입니다. 아직 이 자료에서 거래처·품목·수량·납품 정보를 해석하거나 기존 발주함의 확인 대기 건을 자동 생성하지 않습니다.
3. 대시보드의 발주 알림을 열면 승인 대기 발주 수와 목록이 표시됩니다. 새 발주가 서버에 저장되면 화면 알림이 표시됩니다. 최초 접속 시 기존 발주를 새로 수신한 것처럼 알리지 않습니다.
4. 발주 알림 또는 공유된 `/orders?order=발주번호` 주소를 열어 해당 발주로 바로 이동합니다. 미로그인 상태에서는 로그인 후 같은 발주로 돌아옵니다. 주소를 안다고 내용이나 승인 권한을 얻지는 않습니다.
5. **발주 목록·처리** 탭에서 별도로 등록된 발주를 선택하여 원문과 상세를 대조하고, 오류나 누락을 수정하여 저장합니다. 선택한 메일과 등록 발주는 아직 서로 연결되지 않으며 탭 전환으로 연결이나 자동 해석이 이루어지지 않습니다. 가상 발주는 이후 확인 흐름을 시험하고 수동 보완 등록은 누락 건을 보완하는 용도이며, 테스트 여부는 저장 후 변경할 수 없습니다. 원문·거래처, 품목·수량, 배송 정보 세 가지를 직접 확인한 뒤 내용을 확정합니다. 수량·단위·날짜·수령인·연락처·배송 방법 등이 미확정이면 승인되지 않습니다. 방문 수령 외 배송에는 주소가 필요합니다. "발주 담당자"는 업무상 역할을 뜻하며, 현재 접근 권한은 아래의 매니저·관리자 규칙을 따릅니다.
6. 정보가 부족하면 사유를 남겨 추가 확인으로, 진행하지 않을 건은 사유와 함께 반려로 처리합니다. 알림을 읽거나 공유 링크를 열기만 해서는 승인되지 않습니다.

브라우저 알림은 사용자가 알림 버튼에서 직접 허용한 경우에만 표시합니다. HTTPS 및 브라우저 지원이 필요하며 웹앱이 열려 있는 동안에만 작동합니다. 앱을 닫은 상태의 푸시, 아이폰 잠금 상태의 백그라운드 푸시, 카카오톡·알림톡 자동 전송은 이번 범위에 없습니다. 카카오톡 등에 전달할 때는 검토 링크·요청 문구를 복사해 지정한 담당자에게 직접 전달합니다. 자동 전송을 연결할 때도 로그인과 권한 확인은 그대로 유지해야 합니다.

## 저장·권한·정확성

- `orderRequests/{id}`: 스키마 1, 거래처·수신경로·발주 원문·원문 위치 설명, 서버 접수 시각, 작성자, 내용 버전(`revision`), 상세(`draft`), 검토 상태·확인 항목·검토자·시각·승인 버전을 저장합니다. 원문 위치는 메모이며 URL을 자동으로 열거나 외부 내용을 가져오지 않습니다. 개인정보가 포함된 원문은 승인된 매니저·관리자만 읽을 수 있습니다.
- 상세는 납품일, 배송 방법, 수령인·연락처·주소, 최대 5개 품목으로 구성합니다. 6개 이상인 발주는 원문 전체를 보존한 채 상세를 비워 접수하고 추가 확인으로 보류합니다. 목록을 자르거나 별도 주문으로 임의 분할하지 않습니다. 이 제한은 첫 단계의 서버 검증 계산 한도에 맞춘 것이며 다음 단계에서 확장할 수 있습니다. 모르는 수량은 0으로 임시 저장할 수 있지만 승인할 수 없습니다. 단위 환산·거래처 규칙·상품코드·가격을 자동 추정하지 않습니다.
- 거래처·수신경로·원문·작성자·최초 접수 시각·테스트 표시는 변경할 수 없습니다. 잘못 접수한 원문은 사유를 남겨 반려하고 새로운 건으로 접수합니다. 발주와 이력은 삭제할 수 없습니다.
- 상세 변경은 버전을 1 올리고 승인 대기 상태로 되돌립니다. 이전 문서 전체를 `orderRequests/{id}/versions/{이전버전}`에 같은 거래로 보관해야 서버가 변경을 허용합니다. 이전 검토·승인 증거가 이력에 남고 이력은 수정·삭제할 수 없습니다. 현재 화면에는 이력 조회 화면이 아직 없습니다.
- 검토는 서버 거래에서 읽은 최신 버전에 대해서만 적용됩니다. 화면에서 본 갱신 시각·상태도 비교해 다른 담당자가 검토 중 남긴 변경을 덮어쓰지 않습니다. 동시에 내용이 바뀌면 최신 정보를 다시 확인해야 합니다.
- 인터넷 연결이 없으면 저장·승인을 시작하지 않습니다. 서버 연결 확인 전의 캐시, 저장 대기 중인 내용은 확정 상태와 구분합니다. 서버 거래가 실패하면 완료로 표시하지 않습니다.
- 승인된 활성 매니저·관리자만 생성·조회·수정·검토할 수 있습니다. 일반 직원·승인 대기 계정에는 이 발주함 접근 권한을 부여하지 않았습니다. 추후 역할을 나눌 때는 화면과 보안 규칙을 함께 변경해야 합니다.

## 연결 경계와 배포

브라우저 Firebase 클라이언트와 Firestore 보안 규칙을 사용하며 서비스 계정 키나 ERP 비밀키를 브라우저에 추가하지 않습니다. 웹앱 배포와 함께 `firestore.rules`의 새 발주 규칙도 적용해야 합니다. 적용 전에는 발주 목록·접수 기능이 권한 오류를 보일 수 있습니다. 기존 HACCP 규칙과 별도 컬렉션으로 분리했습니다.

향후 메일 등의 수집 서버는 동일한 승인 대기 스키마로 접수하고 원문 식별자를 이용해 중복 수신을 제어해야 합니다. 현재 직접 접수에는 자동 중복 판별이 없으므로 실제 발주를 반복해서 접수하지 않도록 확인해야 합니다. 카카오 자동 알림은 정식 발송 계정·수신자 연결·템플릿과 서버 측 발송 이력·재시도 체계를 마련한 뒤 별도로 연결합니다. 발주 알림의 읽음 상태는 담당자의 브라우저에 보관하는 편의 기능이며 업무 승인 기록은 Firestore 문서가 기준입니다.

## 네이버웍스 메일 연결

첫 연결 대상은 회사의 네이버웍스 발주 수신 계정입니다. 실제 계정 인증·메일함 조회가 성공하기 전에는 "연결 완료"나 "자동 수집 중"으로 표시하지 않습니다. 연결 점검, 메일 수집, 내용 추출, 담당자 확정은 각각의 성공 여부를 구분해야 합니다.

- 회사 Developer Console에 OAuth 앱을 만들고 HTTPS Redirect URL과 읽기 전용 `mail.read` 권한을 등록합니다. Mail API는 **구성원 계정의 OAuth Authorization Code 인증만 지원하며 서비스 계정 JWT는 지원하지 않습니다**. 수신 계정으로 로그인·동의한 뒤 서버가 토큰을 관리합니다. 회사의 실제 계약·상품을 추정하여 지원 여부를 단정하지 않고, 해당 Console의 권한 제공 여부와 메일함 조회로 확인합니다. [Mail API](https://developers.worksmobile.com/kr/docs/mail), [OAuth 인증](https://developers.worksmobile.com/kr/docs/auth-oauth), [지원 권한 표](https://developers.worksmobile.com/kr/docs/auth-scope)
- Client Secret과 토큰은 서버 전용 비밀 설정에 보관하며 브라우저·저장소·응답·로그에 노출하지 않습니다. Access Token의 만료를 확인하고 Refresh Token으로 갱신합니다. Refresh Token은 90일 유효하며, 회전 설정이 켜져 있으면 응답의 새 Refresh Token을 영속 저장해야 합니다. 환경변수만 사용하는 일회성 연결 점검을 무인 운영 완료로 간주하지 않습니다. 갱신 실패·재인증 필요 상태는 담당자에게 알려야 합니다. [토큰 갱신](https://developers.worksmobile.com/kr/docs/auth-oauth#refresh-access-token)
- 서버는 `GET https://www.worksapis.com/v1.0/users/{수신계정}/mail/mailfolders`로 **지정된 수신 계정**의 접근을 확인하고, 선택한 메일함의 `/users/{수신계정}/mail/mailfolders/{folderId}/children`을 조회합니다. 로그인한 사용자의 프로필 신원을 추가로 검증했다고 표시하지 않습니다. 응답의 `responseMetaData.nextCursor`를 끝까지 처리하고 `계정 + mailId`로 중복 등록을 막습니다. 안 읽은 메일만 수집하면 직원이 먼저 읽은 발주가 누락될 수 있으므로 읽음 여부를 수집 기준으로 삼지 않습니다. 정렬이나 메일 ID의 증가만으로 조회 완료를 추정하지 않습니다. 공개 Mail 명세에 수신 webhook이 명시되어 있지 않아 정기 조회를 우선 검토하며, 조회 실패나 일부 페이지만 처리한 상태를 수집 완료로 표시하지 않습니다. [메일함 목록](https://developers.worksmobile.com/kr/docs/mail-folder-list), [메일 목록](https://developers.worksmobile.com/kr/docs/mail-folder-mail-list)
- 본문은 `/users/me/mail/{mailId}`, 일반 첨부는 `/users/me/mail/{mailId}/attachments/{attachmentId}`로 가져옵니다. API 응답의 발신자·수신 시각·제목·본문·메일 식별자와 첨부 원형을 보존합니다. API가 제공하는 본문을 원본 EML이나 전체 메일 헤더라고 표시하지 않습니다. 다운로드 기한이 있는 첨부와 인라인 이미지는 공식 명세의 별도 방식을 따라야 합니다. 파일 누락·파싱 실패·빈 문서·상충하는 수량·불명확한 거래처는 근거와 함께 추가 확인으로 남기고 임의 보완하지 않습니다. 실제 미확인 첨부가 있으면 확인 전 확정을 막는 처리가 필요합니다. 이는 수집 연결 시 추가할 요건이며 현재 스키마가 첨부 검증을 이미 수행한다는 의미는 아닙니다. [메일 상세](https://developers.worksmobile.com/kr/docs/mail-get), [첨부 다운로드](https://developers.worksmobile.com/kr/docs/mail-attachment-get)
- 연결 시 테스트 메일로 본문·표·첨부와 읽음 상태의 전후 차이, 전체 페이지 수집·중복 방지·실패 후 재시도를 확인합니다. API 상세의 GET이 기존 읽음 표시를 유지한다고 문서만으로 보장하지 않습니다. 실제 수집을 활성화하기 전에 조회 간격·대상 메일함·초기 수집 시작 범위·실패 알림을 정합니다. API 호출 제한과 동시 접속 제한에 맞춰 요청을 제한하고 재시도 간격을 늘립니다. [호출 제한](https://developers.worksmobile.com/kr/docs/rate-limits)

수집은 서비스의 공식 API가 맡고, 일정·재시도·중복 방지·권한·필수 항목 검증은 서버의 명시적 규칙으로 처리합니다. 정형 발주서는 거래처별 규칙으로 읽고, 자유로운 문장·표·이미지는 필요할 때 모델 API로 추출하되 원문 근거와 미확정 값을 함께 남깁니다. AI가 스스로 발주를 확정하거나 승인 범위를 바꾸지는 않습니다. ChatGPT 대화를 계속 실행하거나 PC 화면을 계속 켜두는 것이 수집 서버를 대신하는 구조는 아닙니다.

API 사용이 어려우면 관리자 허용과 외부 앱 비밀번호를 사용하는 공식 IMAP(`imap.worksmobile.com:993`, SSL)을 먼저 검토할 수 있습니다. 브라우저 자동화는 공식 연결이 불가능한 서비스의 보완 수단으로 두고, 로그인 만료·화면 변경·수집 중단을 감지해야 합니다. 현재 이 대안들 역시 실제 계정에 연결하지 않았습니다. [공식 IMAP 설정](https://help.worksmobile.com/ko/use-guides/mail/settings/pop3-imap-smtp/)

### 기본 연결 설정과 시험 수집

사용자는 모든 학교급식 거래처 메일이 **학교급식 발주** 메일함으로 들어오도록 설정했습니다. 현재 회사 메일함 ID는 `106`이며, 수집할 때 같은 ID와 정확한 이름이 유일하게 확인되어야 합니다. 메일함이 없거나 이름·ID가 바뀌면 수집을 멈추며 받은메일함으로 대체하지 않습니다. 학교 수집 요청은 `{folderId:"106",scope:"school"}`이고 상세 메일의 현재 폴더도 정수 `106`인지 다시 확인합니다. 다른 거래 유형을 위한 일반 폴더 수집 API는 유지하지만 현재 화면의 학교 수집은 범위를 바꿀 수 없습니다.

해당 메일함의 최근 7일 메일은 발주 여부와 무관하게 대상입니다. 제목에 ‘발주’가 없다는 이유로 제외하지 않습니다. 기간은 **메일 수신 시각**을 기준으로 하며, 오래된 메일을 오늘 옮긴 것만으로 시험 기간에 포함되지는 않습니다. 폴더에 들어온 사실을 상품 연결이나 발주 확정으로 취급하지 않습니다.

Developer Console 설정은 사용자가 직접 관리합니다.

- Client ID: `kaXX9XpQRZ7ohuKFW1TU`
- 수신 계정: `official@dmnfood.co.kr`

Vercel 프로젝트의 Production 환경에 아래 서버 전용 변수를 설정한 뒤 새로 배포합니다. Client Secret과 수집 계정 비밀번호·암호화 키는 **Secret** 형식으로 저장합니다. 실제 비밀값을 채팅·Git·공유 문서·OneDrive 작업 폴더에 기록하지 않습니다. [.env.example](../.env.example)은 빈 입력 항목과 공개 설정의 목록입니다.

| --- | --- |
| `NAVERWORKS_CLIENT_SECRET` | 사용자가 Console에서 확인한 앱의 Client Secret |

Client ID·수신 계정·Redirect URL은 위 공개값이 기본값입니다. 필요하면 `.env.example`의 같은 이름으로 명시할 수 있으나 현재 Redirect URL은 위 운영 주소만 허용합니다. 암호화 키를 교체하면 기존 암호화 토큰과 진행 중 요청은 사용할 수 없으므로 메일 계정을 다시 연결해야 합니다. 설정이 빠지면 연결·수집 버튼은 사용할 수 없으며, 준비 상태를 연결 성공으로 표시하지 않습니다.

메일 저장 권한을 활성화할 때는 다음 설정을 함께 적용합니다. 기존 발주함·HACCP 권한과 분리한 새 서버 계정·규칙이므로, 실제 운영 활성화 전에 이 범위를 확인합니다.

1. Firebase `dmnfood-haccp` Authentication에 서버 수집 전용 Email/Password 계정을 생성합니다. 실제 직원 계정을 재사용하거나 `users/{uid}` 직원 프로필·관리자 역할을 부여하지 않습니다. 네이버웍스 메일 계정과는 별개인 내부 저장용 계정입니다.
2. 관리자가 Firestore Console에서 `integrationAccess/naverworksMail` 문서에 `collectorUid`(위 UID, 문자열), `enabled`(`true`, 불리언)를 등록합니다. 웹앱과 수집 계정은 이 문서를 생성·수정할 수 없습니다.
3. 준비된 `firestore.rules`를 배포합니다. 전용 UID는 메일 원문·암호화 토큰·일회성 OAuth 상태·작업 잠금·수집 이력만 다룹니다. 기존 발주 승인·HACCP 읽기 권한은 얻지 않습니다. 토큰·OAuth 상태는 직원이나 관리자의 브라우저에서도 읽을 수 없습니다. 원문은 승인된 매니저·관리자가 읽을 수 있으나 변경·삭제할 수 없습니다.
4. Production 비밀 설정 후 새 배포에서 관리자 계정으로 발주함의 **연결 설정**을 열고 **네이버웍스 계정 연결**을 누릅니다. `official@dmnfood.co.kr`의 접근과 학교급식 메일함이 확인되어야 수집을 시작할 수 있습니다. 직원 담당자는 연결 설정 API를 사용할 수 없습니다.
5. 상단의 **메일 가져오기**를 누릅니다. 본문·첨부 정보의 원문 대조와 읽음 상태의 전후 차이를 확인합니다. ‘일부 수집’이면 **이어서 수집**으로 같은 기간의 남은 목록을 가져옵니다. 기존 받은메일함 수집 이력은 학교급식 수집 완료로 표시하지 않습니다.

한 번의 요청은 상세 10건·목록 최대 15페이지·수집 루프 25초 이내로 제한합니다. 기간 밖 메일은 본문을 가져오지 않고 요약 목록만 확인하므로, 과거 메일이 많은 메일함에서도 불필요한 요청 재개를 줄입니다. 최초 요청 시의 시작·종료 시각을 7일 구간으로 고정하며, 재개 요청은 같은 관리자·메일함·수집 범위에 묶이고 1시간 뒤 만료됩니다. 재개할 목록의 남은 메일 ID·수신 시각을 서명된 요청에 고정하여 새로 도착한 메일 때문에 페이지 내 위치가 바뀌어 건너뛰는 문제를 막습니다. 서비스 자체의 페이지 커서는 전체 메일함의 고정 스냅샷을 보장하지 않으므로 운영 정기 수집에는 겹치는 기간의 반복 조회·중복 제거와 누락 점검이 추가로 필요합니다. 네트워크 오류나 실행 중단 후에는 새로 조회해도 이미 보관된 원문을 덮어쓰지 않습니다.

`mailIntakes/{계정과메일ID의SHA256}`에 API 응답 본문·발신자·제목·수신 시각과 첨부 **정보**를 불변 보관합니다. 크기가 큰 원문은 같은 저장 작업으로 분할 저장하며 전체 바이트 수·SHA256으로 검증합니다(현재 최대 4MiB). 원문은 `pending_interpretation`, 최초 첨부 정보는 `metadata_only` 상태를 유지하고 기존 `orderRequests`로 생성하지 않습니다. 원문 메일 열람은 아래 기능으로 제공하며, 거래처 규칙·상품명 별칭 매핑·내용 해석·자동 알림·정기 수집은 다음 단계입니다.

수집 중 확인한 폴더와 원문의 연결은 `mailFolders/{folderId}/intakes/{intakeId}`에 원본 해시와 함께 불변 요약으로 보관합니다. 받은메일함에서 처음 보관한 뒤 학교급식 폴더로 옮긴 메일도 중복 수집 시 연결을 추가하며, 최초 본문·폴더·첨부 기록은 변경하지 않습니다. 연결 저장이 실패하면 수집 완료로 보고하지 않고 재시도로 빠진 연결만 복구합니다. 수집 계정만 원문과 일치하는 연결을 생성할 수 있고, 승인된 매니저·관리자는 읽기만 가능합니다. 이 연결은 **수집 당시 해당 폴더에서 확인했다는 기록**이며 이후 네이버웍스에서 옮기거나 삭제한 사실을 실시간으로 반영하는 목록이 아닙니다.

### 수집 메일 원문과 Excel 열람

- 승인된 관리자·매니저는 `/api/naverworks/source?folderId=106`으로 학교급식 수집 목록을 기본 조회합니다. 전체 보관 목록은 폴더 인자 없이 조회하며, 각 목록은 수신 시각순 20건·동일 시각의 문서 ID순으로 페이지를 나눕니다. 커서는 폴더 범위에 묶여 다른 범위에 재사용할 수 없습니다. `?intakeId=…` 원문 조회와 `/orders?mail=…` 직접 링크는 현재 목록 범위와 별개로 유지합니다. 목록에는 본문·인증 정보를 포함하지 않습니다. 원문은 저장 청크의 바이트 수·SHA256을 재검증한 뒤 반환합니다.
- 본문은 웹앱 안에 삽입하거나 서식·텍스트 보기로 표시하지 않습니다. **네이버웍스에서 메일 열기**는 저장된 숫자 `mailId`만 사용해 고정 주소 `https://mail.worksmobile.com/read/popup?nMailId=…`를 새 창으로 엽니다. 본문이나 외부 URL을 연결 주소로 사용하지 않으며 네이버웍스 로그인 권한은 별도로 필요합니다. 서버에 보관한 API 응답 본문은 그대로 유지합니다. 이를 원본 EML이나 원래 화면과 동일한 캡처라고 표시하지 않습니다.
- 일반 `.xlsx`, `.xls`, `.csv` 첨부는 최대 3MiB까지 담당자가 열람·다운로드를 선택할 때 가져옵니다. 원문에 보관된 첨부 ID·이름·형식·크기만 사용하며 요청자가 전달한 URL은 사용하지 않습니다. 공식 첨부 API의 Base64 응답과 원문 파일명·실제 바이트 수가 일치해야 보관합니다.
- 파일은 `mailIntakes/{id}/attachments/{attachmentId}`와 하위 `chunks`에 별도로 불변 보관하고 SHA256을 남깁니다. 원문 메일 기록을 수정하지 않습니다. 다시 열 때도 저장된 파일과 청크의 무결성을 검사하며 브라우저에서 한 번 더 확인한 바이트만 표시·다운로드합니다. 수집 계정은 파일을 생성할 수 있으나 수정·삭제·발주 승인 권한을 얻지 않습니다.
- Excel 셀 미리보기는 별도 작업 스레드에서 읽으며 수식·매크로·외부 링크를 실행하지 않습니다. 원본 행·열 주소, 시트 선택, 병합 셀, 저장된 표시값, 숨김 시트·행·열 경고를 제공합니다. 큰 시트는 행·열 구간을 나눠 표시하고 전체 범위와 현재 범위를 명시합니다. 서식·이미지·차트·인쇄 배치가 원본과 다를 수 있어 원본 다운로드를 함께 제공합니다.
- 일상 열람 화면에서는 용량 한도·구현 설명·중복 파일명과 저장 버튼을 반복 표시하지 않습니다. 파일명과 열람·다운로드 동작, 시트·표·현재 범위를 중심으로 보여 줍니다. 실제 오류나 숨김 자료·미확정 계산값 등 확인이 필요한 상황의 안내는 유지합니다. 내부 크기·무결성 검증은 그대로 적용합니다.
- 수식 저장값은 오래되었을 수 있으며 계산값이 없는 셀을 수량으로 확정하지 않습니다. 파싱 한도·시간 초과·손상 파일은 성공으로 표시하지 않습니다. 인라인 이미지·기한부 대용량 첨부·기타 파일 형식과 크기 초과 파일은 현재 웹 열람 대상이 아니며 별도 원본 확인이 필요합니다.
- `.xls` 확장자지만 실제로 HTML/XML 표인 파일은 형식을 구분해 읽습니다. 여러 HTML 표처럼 누락 없이 해석을 보장할 수 없는 형식은 미리보기를 중단합니다. 파일의 원본 바이트는 변경하지 않습니다.
- SheetJS CE 0.20.3은 공식 배포본을 로컬에 포함합니다. 파일을 외부 문서 서비스로 보내거나 공개 URL에 업로드하지 않습니다. 이 열람 기능에는 상품 연결·수량 합산·제품별 확인·ERP 전송이 없습니다.

OAuth 토큰은 AES-256-GCM으로 암호화하고, 일회성 상태·보안 쿠키와 시작한 관리자의 권한 재검증을 적용합니다. 동시 수집을 잠그고 회전된 갱신 토큰을 메일 조회보다 먼저 저장합니다. 운영 원문·인증 정보·메일 API 응답은 로그에 출력하지 않습니다. 연결을 중단할 때는 `integrationAccess/naverworksMail.enabled=false`로 저장 권한을 닫고 네이버웍스 앱 동의를 해제할 수 있습니다.

## 검증

화면은 공통 `dashboard/style.css`의 배경·색상·글꼴·입력창 변수를 사용합니다. 메인 카드, 발주함, 알림 창은 같은 어두운 테마와 시안 강조색을 따릅니다. 모바일에서는 목록과 상세, 좁은 화면의 입력 항목을 한 열로 표시합니다.

기본 화면은 작은 메일 상태 영역과 하나의 **발주함**으로 구성합니다. 왼쪽 메일 목록과 오른쪽 **첨부 원본 확인 / 발주 목록·처리** 탭을 사용하며, 관리자 연결 설정은 기본 화면에서 분리한 네이티브 대화상자로 엽니다. 탭을 바꿔도 열어 둔 원본 미리보기와 저장 전 발주 수정 내용은 유지합니다. `/orders?mail=…`과 `/orders?order=…` 직접 링크를 보존하되, 메일과 발주의 업무상 연결을 의미하지 않습니다.

로컬 화면 검증: `node tests/order-ui-server.mjs` 실행 후 `http://127.0.0.1:4175/home`에서 발주 카드를 눌러 이동합니다. `/orders?verificationRole=admin`은 미설정 관리자 화면, 같은 주소에 `&mailScenario=connected`를 추가하면 가상 연결·부분 수집·재개 흐름을 시험합니다. 이 서버는 허용된 화면 파일과 가상 담당자·메모리 데이터만 제공하며, 테스트 표시가 없는 접수를 거부합니다. 사용자 관리와 실제 외부 연결은 실행하지 않습니다. 테스트 서버·가상 모듈은 운영 배포에 포함하지 않습니다.

일반 검증: `node --test tests/order-requests.test.mjs tests/order-notifications.test.mjs tests/auth-session.test.mjs`

메일 연결 검증: `node --test tests/naverworks-core.test.mjs tests/mail-connection.test.mjs tests/mail-integration-store.test.mjs tests/mail-integration-rules.test.mjs`. 저장·규칙 통합 검증은 `MAIL_FIRESTORE_EMULATOR_HOST=127.0.0.1:8789`를 지정하고 격리된 `demo-mail-integration` 프로젝트에서만 실행합니다. 사용자 역할·전용 수집 계정의 격리, 원문 불변·분할·중복, 일회성 OAuth·만료·쿠키·관리자 권한 회수, 암호화 무결성·갱신 토큰 회전, 읽음 포함 기간 조회·페이지 재개를 검증합니다. 단위 시험은 네이버웍스 가짜 응답을 사용하며 실제 계정 인증 성공을 증명하지 않습니다.

원문·첨부 열람 검증: `node --test tests/mail-source-api.test.mjs tests/mail-source-ui.test.mjs tests/mail-workbook-preview.test.mjs`. 원문 목록·페이지 이동·메일 ID 결합, 읽기 역할, 첨부 크기·Base64·무결성·불변 보관, 실제 압축 해제 한도, 여러 시트·숨김·병합·저장 수식값과 미지원 형식을 확인합니다. 소형 파일에서도 ZIP64 항목 크기 확장 정보를 쓰는 ERP 내보내기 형식은 별도 가상 회귀 자료로 검증합니다. 실제 업무 파일을 테스트 자료나 저장소에 복사하지 않습니다.

운영 화면에서는 실제 거래처 ERP 내보내기 Excel 1종(1개 시트·5행·9열)과 거래처 자체 양식 1종(3개 시트)의 첨부 보관·셀 표시·원본 다운로드 경로를 별도로 확인했습니다. 이 확인은 상품 해석·수량 합산·발주 승인·ERP 전송 검증을 뜻하지 않습니다.

규칙 검증은 `demo-order-notifications` 프로젝트 이름의 격리된 로컬 Firestore 에뮬레이터에서만 수행합니다. 로컬 에뮬레이터를 `127.0.0.1:8788`에 최신 `firestore.rules`로 시작한 뒤 PowerShell에서 `$env:ORDER_FIRESTORE_EMULATOR_HOST='127.0.0.1:8788'; node --test tests/order-requests.test.mjs`를 실행합니다. 이 변수가 없으면 규칙 통합 시험은 건너뜁니다. 통합 시험은 외부 Firebase 호스트를 허용하지 않습니다. Windows에서 에뮬레이터의 한국어 진단 리소스 문제가 발생하면 Java 옵션 `'-Duser.language=en' '-Duser.country=US'`를 사용합니다.

검증 범위: 미확정 상세와 불가능한 날짜, 수량·단위·연락처 누락 차단, 확인 세 항목 강제, 최대 품목 수, 잘못된 역할과 비활성 승인 계정 차단, 원문 변경 금지, 오래된 버전·갱신 시각 차단, 내용 변경 시 승인 초기화, 이전 승인 이력의 원자적 보관·수정 삭제 금지, 오프라인 승인 금지, 캐시와 서버 확인 상태 구분. 실제 수집 서비스·ERP·프린터·메신저 또는 운영 계정에 대한 쓰기는 시험하지 않습니다.
