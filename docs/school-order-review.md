# 학교급식 발주: 원문 근거를 함께 확인하는 흐름

이 문서는 2026-10-21에 설명받은 업무 규칙과 다음 구현의 설계 기준이다. 행별 강조·제품 확인·해석·ERP 전송은 아직 운영 기능이 아니다. 현재 구현은 네이버웍스 계정 연결, 선택 메일함의 최근 7일 본문·첨부 정보 수집, 수집 본문 열람과 지원하는 일반 Excel 첨부의 원본 보관·셀 미리보기다. Excel 미리보기는 원본과 서식이 다를 수 있으며, 행별 상품 연결·확정 기능과 구분한다.

## 확정된 업무 규칙

- 기본 발주는 거래처가 일주일치를 보내는 주 1회 발주다. 이후 추가·수정 자료가 올 수 있다. 주 1회라는 이유로 두 번째 자료를 중복으로 버리지 않는다.
- 메일은 거래처 ERP(주로 dotop)의 링크와 Excel 첨부, 거래처 자체 양식, 제목에 품목·수량을 적는 형태가 있다.
- 2026-10-21 사용자가 모든 학교급식 거래처 메일을 네이버웍스 **학교급식 발주** 메일함으로 들어오도록 설정했다고 확인했다. 학교급식 단계의 수집 범위는 이 메일함을 기준으로 한다. 현재 확인한 메일함 ID는 `106`이며, 수집 시 같은 이름·ID가 확인되어야 한다. 해당 폴더에 들어온 사실을 상품 연결이나 발주 확정으로 취급하지 않는다.
- 카카오톡은 주로 Excel·발주서의 캡처 이미지이며, 문자는 주로 상품과 수량이 적힌 텍스트다. 해당 채널은 아직 수집 연결 전이다.
- 거래처 상품명과 회사 상품명은 다르다. 실제 상품명 대응표는 사용자가 별도로 제공한다. 임의의 실제 매핑을 만들지 않는다.
- 수량은 **항상 각 행의 수량 칸을 합산**한다. 제품이 등장한 행 수를 수량으로 사용하지 않는다.
- 발주 담당자(사무 담당자와 대표)가 자동 인식 내용을 원문과 함께 대조한다. 담당자의 수동 등록 후 다른 사람에게 결재받는 흐름이 아니다.

## 화면의 진행 순서

1. 자료 도착과 보관 상태를 알린다. 해석 중·확인 준비·추가 확인 필요를 구분한다. 제목·첨부를 받았다는 사실을 발주 내용을 정확히 인식했다는 뜻으로 표시하지 않는다.
2. 거래처·대상 주간·자료 종류·신규/추가/수정 관계를 확인한다. 원본 파일·페이지·시트가 모두 준비됐는지 확인한다.
3. 원문 왼쪽과 해석 결과 오른쪽을 함께 표시한다. 같은 회사 제품으로 인식한 모든 행을 동시에 강조한다. 상품명뿐 아니라 수량·단위·규격의 근거도 표시한다.
4. 제품별로 각 행의 수량과 합산식을 보여준다. 예: `2행 2병 + 3행 1병 + 5행 3병 = 6병`. 담당자가 수정하거나 원문 대조 완료를 누르면 다음 제품으로 이동한다.
5. 모든 원문과 제품의 대조가 끝나면 원문 화면에서 최종 결과 화면으로 이동한다. 제품별 합계와 원래 납품 일정·납품처 내역을 함께 확인한다.
6. 최종 확인된 버전을 고정하고 서버가 ERP 전송 작업을 만든다. 등록 중·등록 확인·일부 실패·등록 여부 확인 필요를 구분하고 실제 전표 식별자를 결과에 연결한다.

제품별 묶음은 확인 편의를 위한 단위다. 거래처 발주서의 납품일·학교·납품처 정보는 원래 행에 남긴다. 거래처의 학교 납품일과 우리 회사의 출고일·ERP 전표일은 별도 개념이다. 최종 ERP 집계 단위와 전표일은 실제 회사 업무에 맞춰 설정한다.

## 자료별 원문 근거

| 자료 | 원문 보관 | 강조할 위치 |
| --- | --- | --- |
| Excel | 첨부 파일 자체와 해시, 형식을 유지한 열람 자료 | 파일·시트·행·상품/수량/단위/날짜 셀 범위 |
| 이미지·PDF | 원본 파일과 해시, 원본 크기 | 페이지와 원본 좌표에 연결된 영역 |
| 제목·본문·문자 | 필드별 원문 문자열과 해시 | 해당 필드의 문자 구간 |

Excel을 임의로 재구성한 표는 원본 그대로라고 표시하지 않는다. 실제 원문 열람에서는 병합 셀, 숨김 행·시트, 여러 페이지, 잘린 이미지까지 확인 범위를 관리한다. 수량 셀의 수식·표시값이 다르거나 읽을 수 없으면 미확정으로 남긴다.

메일 본문, ERP 링크, Excel 첨부에 같은 주문이 반복되어도 각각 별도 발주 수량으로 합산하지 않는다. 거래처 양식별로 계산 기준 자료를 정하고, 같은 내용의 표현은 근거로 연결한다. ERP 접근 버튼은 발주서 데이터이며 임의 외부 접속·입력 명령으로 취급하지 않는다.

## 상품·수량 해석과 누락 방지

- 거래처별 상품명 대응표에는 원문 이름·원산지·규격·포장·단위와 회사의 정확한 품목 코드를 연결한다. 원문 이름이 비슷하다는 이유만으로 다른 상품을 합치지 않는다.
- 단위가 다르면 승인된 환산 규칙을 먼저 적용한다. 박스당 병 수가 정해지지 않았으면 합산·확정을 막는다. 원문 수량과 환산 결과, 사용한 규칙을 함께 남긴다.
- AI는 상품·수량·근거 위치의 후보를 제안한다. 합계는 확정된 행의 값을 프로그램으로 계산한다. AI가 만든 합계 숫자만 승인 근거로 사용하지 않는다.
- 대상 범위의 행/영역은 `제품 수량에 포함 / 사유를 남기고 제외 / 미해결` 중 하나에 속해야 한다. 미해결을 숨기거나 0으로 바꿔 최종 확인을 통과시키지 않는다.
- 제목·헤더·소계·합계 행은 상세 행과 중복 합산하지 않는다. 다른 업체 상품은 거래처 규칙과 원문 근거로 제외하며, 우리 상품인지 불명확한 행은 확인 대상으로 남긴다.
- 파일·페이지·시트 누락, 읽을 수 없는 수량, 미확정 상품, 불명확한 단위가 있으면 최종 확인을 막는다.

## 추가·수정 발주

거래처, 발주번호, 대상 주간, 학교·납품처 등을 이용해 기존 발주와의 관계 후보를 찾는다. 자료 도착 시각만으로 이전 발주를 덮어쓰거나 주간 합계에 더하지 않는다.

| 구분 | 확인할 의미 |
| --- | --- |
| 신규 | 별개의 새 주문 |
| 추가 | 기존 수량에 더할 수량 |
| 전체 교체 | 새 자료가 기존 전체 내용을 대체 |
| 일부 수정 | 지정한 행·제품·일정만 변경 |
| 취소 | 지정한 범위의 취소 |
| 관계 미확정 | 담당자가 의미를 확인하기 전 처리 보류 |

예를 들어 기존 6병에 새 자료가 2병이라고 적혀 있어도, 추가라면 8병이고 전체 수정이라면 2병이다. 변경 화면에는 이전·변경 후 수량·증감과 두 원문을 함께 표시한다. 원문과 이전 확인 버전은 보존한다. ERP 입력 뒤 도착한 수정 자료는 새 판매 전표를 무조건 추가하는 대신 회사의 정정 절차로 연결한다.

## 확인 기록과 ERP 전송

제품 확인은 `원문 해시 + 해석 버전 + 상품 대응표 버전 + 대상 행 + 계산 결과`에 결합한다. 상품·수량·근거가 바뀌면 해당 제품의 확인과 전체 최종 확정을 해제한다. 다른 담당자의 변경은 현재 발주함의 버전 충돌 방지 방식을 확장해 처리한다.

ERP 전송은 다음 조건을 만족해야 한다.

- 담당자가 최종 확인한 동일 버전만 서버가 전송한다. 브라우저에서 넘어온 임의 품목·수량을 그대로 ERP에 쓰지 않는다.
- 거래처 코드, 회사 품목 코드, 단위, 전표일, 창고·단가·세금 등 회사 필수 항목을 검증한다. 상품 대응표를 받기 전에는 실제 코드로 자동 매핑하지 않는다.
- 발주·확정 버전·ERP별로 하나의 전송 작업을 만들고 중복 클릭·동시 실행을 막는다.
- 요청 시간 초과는 등록 실패로 단정하지 않는다. 이미 등록됐을 수 있으므로 자동 재전송하지 않고 등록 여부를 대조한다.
- HTTP 성공만으로 등록 완료라 하지 않는다. 항목별 처리 결과와 실제 전표 식별자를 확보한다. 일부 성공이면 성공·실패 항목을 분리한다.
- 최종 확인 뒤 ERP 전송 전 수정 자료가 도착한 경우, 기존 전송 작업과의 관계를 확인할 수 있도록 보류 상태를 둔다.

이카운트 공식 안내에는 판매 입력 API와 사전 테스트가 명시되어 있다. 정확한 요청·응답 규격과 회사 필수값·재조회 수단은 로그인 후 회사 API 매뉴얼로 확인해야 한다. 판매 입력은 재고 차감·미수금 반영을 수반하므로 기존 회사의 판매 전표 종류·기준일·집계 방식을 재현해야 한다.

## 다음 구현의 데이터 경계

1. `수신 자료`: 채널 식별자, 수신 시각, 발신자, 원본·해시와 보관 위치.
2. `문서/행/영역`: 시트·페이지·문자·좌표, 원문 값, 포함/제외/미해결 상태.
3. `해석 버전`: 거래처 양식·상품 대응표 버전, 후보 품목 코드, 수량·단위와 계산 근거, 원래 납품 일정.
4. `검토 버전`: 제품별 확인, 원문 범위 확인, 최종 확정 내용·담당자·시각.
5. `ERP 작업`: 확정 버전과 고정된 전송 내용, 상태·시도·응답·전표 식별자·대사 결과.

현재의 발주 스키마 1은 텍스트 원문, 최대 5품목, 발주 전체에 하나의 납품일을 갖는다. 새 흐름은 UI뿐 아니라 저장 구조·보안 규칙·알림 대상을 함께 확장해야 한다. 수집 계정은 발주를 확정할 권한을 얻지 않으며, 실제 운영 연결 전까지 기존 확인 화면과 서버 권한은 변경하지 않는다.

## 구현 순서

1. 가상 주간 발주서로 동일 제품의 다중 행 강조·수량 합산·수정 후 재확인·최종 합계 흐름을 점검한다.
2. 실제 메일의 Excel 첨부 보관·열람을 연결하고 양식 한 종류를 우선 지원한다.
3. 사용자가 제공한 거래처별 상품 대응표와 실제 발주 양식으로 행별 근거·수량·예외를 검증한다.
4. 검증된 해석 결과를 확인 요청 알림과 연결한다. 정기 수집은 독립된 서버 작업으로 운영한다.
5. 실제 회사 판매 전표와 공식 API 매뉴얼을 기준으로 이카운트 시험 환경에서 전송·대사·중복 차단을 검증한다.
6. 최종 확인된 건의 운영 ERP 전송을 연결한다. 카카오톡 캡처·문자는 같은 근거 확인 구조에 별도 수집 연결을 붙인다.
